# SIGMA Studio 作業計画書

- 文書種別：実装・検証計画
- 対象：SIGMA Studio
- 連携先：SIGMA Core
- 状態：計画書。記載した作業は、個別に実装・テスト・確認するまで完了扱いにしない。

## 1. 目的

SIGMA Studio の既存機能を維持しながら、資料ビューアー、資料からの情報取得、AI への資料引き渡し、SIGMA Core との連携を段階的に整備する。

本書は実装計画であり、記載した機能がすでに実装・検証済みであることを意味しない。着手時にはリポジトリのコード、未コミット変更、テスト、CI を確認して現状を確定する。

## 2. 基本方針

1. 既存の保存・読み込み・編集・提案承認などの主要フローを壊さない。
2. SIGMA Core は資料データの保存・抽出・検索・部分取得を担当し、Studio は UI、表示、操作、AI への引き渡しを担当する。
3. PDF 表示は既存の確定済みページ描画経路を調査して再利用し、第二のページネーション／レンダリングエンジンを安易に作らない。
4. Workspace はユーザーが選択する。自動選択で意図しない資料領域を使わない。
5. ビューアーからのキャプチャー対象は、SIGMA Studio 内の資料ビューアーに表示されている内容だけとする。デスクトップ全体や外部アプリのキャプチャーは対象外。
6. CLI 型 AI と Web AI の扱いを分ける。MCP の直接連携は当面 CLI 型 AI を対象とし、Web AI に MCP 接続がある前提で設計しない。
7. Web AI に資料を渡す場合は、Studio が選択・表示している資料から必要な部分を抽出し、ユーザーが内容を確認できるエクスポート／引き渡し経路を用意する。
8. 新しいファイル形式は段階的に追加し、表示品質と AI 向け抽出品質を別々に評価する。
9. 大きな設計変更は実装前に影響と選択肢を提示し、合意を得る。
10. 実装済み・テスト済み・CI 確認済み・統合確認済み・未確認を区別する。

## 3. 責務の境界

### SIGMA Studio が担当するもの
- 資料一覧と資料選択 UI
- ビューアー表示、ページ移動、ズーム、選択、スクロールなどの操作
- 形式別レンダリングの統合
- 表示中の資料内容に限定したキャプチャー
- 選択ページ／範囲／テキストの確認とエクスポート
- CLI AI／Web AI ごとの資料引き渡し UI
- Core API の呼び出し、状態表示、エラー表示
- ユーザーによる Workspace 選択

### SIGMA Core が担当するもの
- 原本保管、メタデータ、整合性管理
- テキスト抽出と出典位置情報
- 検索、ページ・範囲単位の部分取得
- AI 向け資料パッケージ生成に必要なデータ API
- 永続化・抽出・検索のテストとデータ契約

### 境界要件
- Studio は Core の内部 DB に直接依存せず、公開 API／型契約を利用する。
- Core にビューアー UI や Studio 固有の画面状態を持たせない。
- Studio 側の既存ストアを Core に置き換える場合は、移行手順、互換性、ロールバック方法を別途定義する。
- 資料本文を外部 AI に送信する場合、送信対象と送信先がユーザーに分かる設計にする。

## 5. Phase 1：ビューアーと資料形式の契約

目的：各形式を共通の UI 操作で扱えるようにしつつ、形式固有の制約を隠しすぎない。

作業：
- 資料 ID、形式、表示名、原本バージョン、読み込み状態を共通モデルとして整理
- 各ビューアーに共通する操作（次／前、ページ・位置、選択、検索等）を整理
- 形式ごとにサポート可能な操作を明示
- 表示エラー、未対応形式、読み込み中、空資料、破損資料の状態を定義
- 既存 SigmaDoc viewer と他形式の責務を整理

受け入れ条件：
- 形式ごとの対応機能が明示される
- 未対応操作を動作するように見せない
- 既存の SigmaDoc の主要フローが維持される

## 6. Phase 2：PDF 表示経路の安定化

目的：既存 PDF 表示方式を再利用し、ページ表示と Core の抽出位置を混同しない。

作業：
- 既存の PageCanvas／ページ描画セッション等の実装と呼び出し元を確認
- 第二のページネーションエンジンを作らず、既存経路を拡張できるか評価
- PDF ページ番号、表示状態、選択範囲、Core の抽出ページ番号の対応を定義
- 大きな PDF、ページ移動、ズーム、連続スクロール時の負荷を測定
- ページ表示と抽出テキストの同期・非同期状態を分離
- PDF の描画失敗とテキスト抽出失敗を別々に扱う

受け入れ条件：
- ページ番号が元 PDF と一致する
- 既存の描画経路を壊さない
- 表示と抽出の失敗が区別され、エラーが適切に表示される
- Electron 上で動作を確認する

## 7. Phase 3：段階的な形式対応

候補形式は現状調査と依存関係の確認後に確定する。優先候補：

1. PDF
2. TXT、Markdown、CSV
3. HTML
4. DOCX
5. XLSX
6. PPTX
7. 画像／OCR
8. その他の形式

形式ごとに以下を別々に評価する。
- ビューアーでの表示忠実度
- テキスト抽出の精度
- ページ・段落・シート・セル・スライド等の出典位置
- 選択範囲とコピー／エクスポートの品質
- 大容量・破損・パスワード保護ファイルへの挙動
- ライブラリのライセンス、保守状況、依存サイズ、Electron 互換性

受け入れ条件：
- 「表示対応」と「AI 抽出対応」を区別して記録する
- 対応済みとする形式は代表サンプルと異常系テストを通過する
- 制約と未対応機能を文書化する

## 8. Phase 4：ビューアー内の選択・キャプチャー

目的：ユーザーが見ている資料の必要な部分だけを AI へ渡せるようにする。

作業：
- ビューアー内で選択できる対象を定義（テキスト、ページ、範囲、表など）
- キャプチャー結果に資料 ID、原本バージョン、ページ／範囲などの出典情報を付与
- キャプチャー対象をビューアー領域に限定
- 表示された内容と抽出テキストが異なる場合の扱いを定義
- ユーザーが送信前に内容を確認・修正できるプレビューを設ける
- 選択できない形式ではページ単位やテキスト抽出などの代替手段を示す

受け入れ条件：
- デスクトップ全体や外部アプリをキャプチャーしない
- 取得内容の出典を追跡できる
- 空の選択、範囲外、抽出不能などを安全に扱う
- ユーザーが送信前に内容を確認できる

## 9. Phase 5：Core 読み取り連携

目的：Core のデータ契約を通じて資料一覧・抽出結果・部分取得を利用する。

作業：
- Core API／adapter の型とエラー契約を確認
- 資料一覧、メタデータ、抽出テキスト、部分取得を接続
- Core が未起動・未接続・エラーの場合の UI 状態を定義
- 原本バージョンと表示中の資料バージョンの不一致を検出
- 読み取り PoC と既存ストアの全面移行を分離
- データ移行を行う場合は対象、バックアップ、ロールバックを事前に定義

受け入れ条件：
- Studio が公開契約経由で資料を取得できる
- Core の内部 DB に直接依存しない
- 接続失敗が既存機能全体のクラッシュにつながらない
- PoC の成功を全面移行完了と誤認しない

## 10. Phase 6：AI への資料引き渡し

目的：CLI AI と Web AI の違いを明確にし、必要な資料だけを安全に渡す。

### CLI 型 AI
- CLI AI が Core／MCP を利用する構成を検証
- MCP のツール一覧、引数、戻り値、エラーをテスト
- 資料 ID・出典位置を失わずに AI に渡す
- 権限・対象資料・処理結果を追跡できるログ方針を定義

### Web AI
- Web AI から MCP に直接接続できる前提を置かない
- Studio で選択した資料部分をエクスポート／コピー等で引き渡す
- 送信前に本文と出典情報を確認できるようにする
- 外部送信されるデータの範囲をユーザーに明示する
- Web AI ごとの入力制限に応じてサイズ制限や分割を行う

受け入れ条件：
- CLI AI と Web AI の経路が混同されていない
- AI に渡した内容と元資料の出典を追跡できる
- 送信失敗・サイズ超過・資料更新を処理できる
- ユーザーの意図しない資料を自動で送信しない

## 11. Phase 7：Workspace と共通データ利用

作業：
- Workspace 選択 UI と選択状態のライフサイクルを確認
- 自動選択を行わず、未選択時の挙動を明示
- Core の共通 DB と Workspace の文脈を区別
- Workspace 切り替え時に前の資料・選択範囲が誤送信されないことを確認
- 権限や資料スコープを持つ場合、その適用点を文書化

受け入れ条件：
- Workspace はユーザーが選択できる
- 未選択時に暗黙の Workspace を使わない
- 切り替え後に以前の資料が意図せず AI 入力に残らない

ユニットテスト：

- ページ・範囲・選択情報の変換
- Core API の正常系・異常系
- AI 引き渡しデータのサイズと出典情報

統合テスト：

- Core から抽出結果・指定範囲を取得する

- Core 未接続・破損資料・未対応形式
- Workspace 切り替え
- 既存の保存・読み込み・編集・マージ・提案承認の回帰

## 13. 非機能要件

- メモリ 8 GB 程度の環境でも過剰な常駐メモリ消費を避ける
- 大きな資料の読み込み・レンダリング・抽出は段階処理し、UI の応答性を保つ
- ビューアーのエラーがアプリ全体のクラッシュにつながらないようにする
- ファイル本文や個人情報をログへ無条件に出力しない
- 外部 AI への送信対象と送信先を明示する
- 新規依存はライセンス、保守状況、パッケージサイズ、Electron 互換性を確認する
- UI の改善はアクセシビリティ、キーボード操作、エラー表示も含めて確認する

## 14. 優先順位

- **P0：** 現状調査、テスト基準取得、PDF 描画経路と既存保存フローの把握、Core 契約確認

- **P3：** Office 形式の拡張、OCR、パフォーマンス改善、高度な検索 UX

Phase 0 の結果により順序を更新する。
